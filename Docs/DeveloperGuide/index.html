01

The golden rule

Preserve the business behavior from PTLMFGERP Web Forms, but implement it using the existing PTLMFGPLUS MVC architecture. Never carry ViewState, control events, or page lifecycle code into MVC.

01

Architecture

Keep the complete request path visible

A feature is incomplete when only the screen or controller is implemented.

Trust boundary

Server owns authority

Resolve company, user, and permissions from the authenticated server context. Never trust posted COMCOD, user ID, totals, or status.

Business boundary

Service owns coordination

Controllers validate the HTTP request. Services coordinate business rules and data access. JavaScript only improves usability.

Data boundary

Stored procedures stay compatible

Preserve procedure name, CallType, parameter meaning, null behavior, result-set order, decimal precision, and transaction boundaries.

02

Reuse before creating

Use the shared function that already owns the concern

Do not create local alternatives for loading, requests, notifications, controls, tables, dates, or footer actions.

03

Frontend structure

Write one private page module

Place scripts in wwwroot/js/J_{AreaName}/j{PageName}.js and expose only init.

Canonical page shape JavaScript 
const commonPath = "/F_07_RM/MaterialTransfer/";

var MaterialTransferPage = (function () {
    "use strict";

    const state = {
        documentId: null,
        lines: [],
        isSaving: false
    };

    const service = {
        async save(request) {
            return Helpers.withLoader(function () {
                return FetchHelpers.postJson(
                    FetchHelpers.urlconfig(`${commonPath}Save`),
                    request
                );
            });
        }
    };

    const ui = {
        setSaving(isSaving) {
            state.isSaving = isSaving;
            document.querySelector("#btnFooterSave").disabled = isSaving;
        }
    };

    const validation = {
        buildRequest() {
            return {
                documentId: state.documentId,
                lines: state.lines
            };
        }
    };

    async function saveDocument() {
        if (state.isSaving) {
            return;
        }

        ui.setSaving(true);

        try {
            const response = await service.save(
                validation.buildRequest()
            );

            Notifications.Toastr.success(
                "Saved",
                response.message
            );
        }
        catch (error) {
            Notifications.handleError(
                error,
                "The material transfer could not be saved."
            );
        }
        finally {
            ui.setSaving(false);
        }
    }

    function bindEvents() {
        document
            .querySelector("#btnFooterSave")
            ?.addEventListener("click", saveDocument);
    }

    function init() {
        bindEvents();
        EnterpriseUI.initialize(document);
        ShowFooterWithButtons();
    }

    return {
        init: init
    };
})();

document.addEventListener(
    "DOMContentLoaded",
    MaterialTransferPage.init
);
State

Mutable page data only

Keep identifiers, rows, selections, and pending flags private. Do not store trusted authorization context or stale DOM nodes.

Service

Network calls only

Return the response. Do not read the DOM, render controls, or silently convert a rejected request into empty data.

UI

DOM work only

Read values, render rows, show states, initialize controls, and manage focus. Use textContent for untrusted values.

Workflow

Coordinate by business verb

Build and validate the request, set pending state, call the service, update state, render, notify, and reset in finally.

✓ Do

  • Bind events once in bindEvents().
  • Use named async workflow functions.
  • Use const; use let only for reassignment.
  • Keep source readable with braces and tags on separate lines.
  • Repeat critical validation and all authorization on the server.

× Do not

  • Use inline onclick or global mutable state.
  • Bind handlers inside rendering loops.
  • Mix callbacks and promises in one workflow.
  • Use setTimeout instead of awaiting real work.
  • Trust client totals, company, user, permission, or record status.
04

HTTP boundary

Keep controllers thin, explicit, and protected

A controller translates HTTP input into a validated service call and a deliberate HTTP response.

Preferred state-changing endpoint C# 
[Authorize]
[Area("F_07_RM")]
public class MaterialTransferController(
    IMaterialTransferService service) : Controller
{
    [HttpPost]
    [ValidateAntiForgeryToken]
    [PagePermission(
        "F_07_RM",
        "MaterialTransfer",
        "Index",
        "",
        PagePermissionAccess.Entry)]
    public async Task<IActionResult> Save(
        [FromBody] SaveMaterialTransferRequest request)
    {
        if (request == null || request.Lines.Count == 0)
        {
            return BadRequest(new ApiErrorResponse
            {
                Message = "Add at least one material line.",
                ErrorCode = "VALIDATION_ERROR"
            });
        }

        SaveMaterialTransferResponse result =
            await service.SaveAsync(request);

        return Ok(result);
    }
}
AuthenticateUse [Authorize].
AuthorizeApply PagePermission to the page and AJAX actions.
ValidateCheck required input, ranges, dates, ownership, and business state.
ProtectUse the project anti-forgery convention on state changes.
Bind safelyAccept request DTOs, not editable database entities.
Respond clearlyUse 400, 401, 403, 404, and 409 deliberately.
Stay thinDo not build DataTables or implement calculations here.
Stay asyncAwait I/O. Never wrap synchronous database calls in Task.Run.
Important: Some legacy controllers return GetError()?.Message or caught exception messages to the browser. Do not copy that pattern into new code. Return a safe business message and let unexpected exceptions reach GlobalExceptionMiddleware for correlation-based logging.
05

Business and data layer

Preserve rules and isolate company data

Use injected services and repositories. Build stored-procedure parameters from trusted context.

Stored-procedure call pattern C# 
public async Task<IEnumerable<MaterialRow>> GetMaterialsAsync(
    string projectCode)
{
    var parameters = new ClassProAccessParams
    {
        StoredProcedure = "SP_ENTRY_MATERIAL_TRANSFER",
        Calltype = "GETMATERIALS",
        Comp1 = common.GetComcod(),
        Desc01 = projectCode,
        UserID = common.GetUserId()
    };

    return await unitOfWork.SP_Call.ListAsync<MaterialRow>(
        parameters
    );
}

Always preserve

  • Stored procedure name and CallType.
  • Parameter order, meaning, and null behavior.
  • Result-set order and typed mappings.
  • Decimal precision and calculation order.
  • Existing transaction boundaries.

Always enforce

  • COMCOD and user ID from ICommonService or trusted context.
  • Company filtering on read, write, lookup, print, and export.
  • Record ownership before update or delete.
  • Parameterized database calls.
  • Explicit DBNull and nullable handling.

Prefer typed results

  • Typed entity or response models for stable shapes.
  • A response object with typed lists for multiple result sets.
  • DataSet only for dynamic or existing integrations.
  • Focused request DTOs to protect server-owned fields.
  • DI registration in ApplicationDI.cs.

Failure behavior

Make failures safe, visible, and traceable

Expected failures get deliberate responses. Unexpected failures get centralized logging and a reference ID.

Adds correlation ID and normalizes HTTP/network errors.

400

Invalid input — explain what the user can correct.

401

Unauthenticated — sign-in is required.

403

Forbidden — permission or company access denied.

404

Not found — authorized record does not exist.

409

Conflict — current business state prevents the action.

500

Unexpected — middleware returns a safe message and trace ID.

✓ Catch when

  • You can recover safely.
  • You convert a known business condition into a deliberate response.
  • You add meaningful context and rethrow.
  • You must restore UI pending state in finally.

× Never

  • Catch Exception and return false, null, or an empty list.
  • Return exception messages, SQL, connection details, or stack traces.
  • Show both a local error and an unhandled rejection.
  • Present a failed load as a valid empty state.
07

Razor and UI

Build calm, dense, predictable ERP screens

Use _AdminLayout.cshtml, shared enterprise classes, and the established application shell.

Readable markupBreak lines between tags. Do not compress a whole table onto one line.
DatesUse Bootstrap Datepicker and display dd-MMM-yyyy.
NumbersRight-align quantities, rates, amounts, and numeric inputs.
ActionsUse the shared footer for page-level workflow actions.
TablesNative table for editable lines; DataTables for read-heavy lists.
FormsUse persistent labels, server validation, and task-sequence field order.
AccessibilityUse semantic elements, visible focus, keyboard order, and labels for icon buttons.
CSSReuse enterprise tokens and classes; avoid inline styles and page-specific control heights.
20

DataTables defaults

Default to 20 rows with page lengths 10, 15, 20, 30, 50, 100, 300. Preserve the current page after a row update when practical.

08

Migration workflow

Investigate before implementing

Migration is behavior discovery first, code writing second.

  1. 1
    Inspect the Web Forms feature

    Read ASPX, code-behind, JavaScript, stored-procedure CallTypes, report definitions, permissions, and linked workflows.

  2. 2
    Inventory every action

    Record load, search, save, update, delete, approve, calculate, print, and export behavior, including validations and result sets.

  3. 3
    Select the MVC page pattern

    Choose operational workspace, transaction entry, master list, report/inquiry, or guided process.

  4. 4
    Trace the full implementation path

    Build View → JS → Controller → Service → repository/stored-procedure mapping. Keep filters and selected IDs explicit.

  5. 5
    Verify behavior, not appearance alone

    Compare calculations, validation, permissions, company isolation, totals, reports, empty data, failed saves, and approval state with Web Forms.

When source behavior is unclear: document the uncertainty and ask for a decision. Do not silently “fix” a business rule during migration.
